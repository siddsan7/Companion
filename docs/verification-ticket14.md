## Behavior and acceptance boundary

Export first previews the actual main-owned application-data location, saved conversation count and vault hints. The UI explains that a vault backup alone omits conversation history. The separate OS save dialog chooses the output. Source conversations, vault files and settings are not copied recursively. Export snapshots and revalidates guarded application records, excludes active/unsaved state, and publishes a synced stage through an exclusive link. Existing destinations are never overwritten. Cancellation has an implemented no-write return; a separate archive cancellation acceptance case has not been run.

Restore inspects a selected file before offering matching. It validates supported format/version, strict UTF-8/JSON, schema whitelist and integrity. It retains the selected ordinary parent identity and exact file-byte digest, then reopens/rechecks at matched preview and under the shared history lock before mutation. Changed, missing or aliased inputs invalidate the review. One-use main-owned confirmation tokens bind the reviewed state. Current history/settings fingerprints, current vault and exact brief pins are rechecked at commit.

Restore uses additions plus explicit Keep current, with no overwrite or semantic merge option. Same-ID equal content is a no-op; differing content defaults unresolved. Every conflict requires its own Keep current choice. Missing history carries an intentional-deletion warning and needs explicit addition consent. New records use synced exclusive stages and links, never the replacing conversation-write path. Partial failure reports the number added and requires another inspection; no automatic retry or pending promotion occurs. Conversation deletion/tombstones and source purge remain #12/#13 responsibilities. File absence alone does not establish deletion consent, and archive copies have a separate lifecycle.

For a moved installation, the user selects an archived binding and explicitly matches the current vault. The reader checks the retained immutable approved brief ID/version/digest in the separately copied vault. Original external brief documents can be missing or outdated without invalidating an intact historical pin. Archive restore never recreates the brief or its source notes. Only the conversation envelope's vault root changes; `archiveBinding` records the archive ID and former root, retaining earlier mapping under `previous`. Request IDs, messages, phases, complete replies, exact packages, pins, dependencies and per-conversation source/history scope stay literal. Archived capacity bindings and provider IDs are historical evidence, not current approvals or permission to replay.

Current vault/parent settings remain selected; changing them uses the normal explicit Choose vault workflow. Optional reviewed note inclusion maps only the chosen binding's archived explicit-note paths into the current vault. Each current eligible ordinary single-link Markdown/text note is shown with full text and digest, initially unchecked. Revalidation includes current bytes, contained ordinary ancestor paths and the existing context-scope kernel lock. The commit adds only checked notes, preserves current conversation exclusions/ledger authority and clears main history/excerpt approvals. Unavailable paths stay excluded. The current per-note review cap is 2 MiB. No whole-vault discovery or source scan is triggered by archive restore.

## Version 1 format and whitelist

`app/archive-format.js` and `app/archives.js` define the current contract. A UTF-8 JSON envelope has `format: "companion-local-history"`, `version: 1`, archive UUID `id`, `createdAt`, `appVersion`, `payload`, `integrity`, and optional `coverage`.

The five payload sections are:

- `conversations`: strict supported schema-1 records, full ordered requests/messages, complete text, historical provider/usage evidence, exact packages, brief pins, dependencies, versioned exclusions and optional mapping provenance. Unknown record/package members are rejected rather than recursively copied.
- `settings`: current `vault` and `parent`; own `codexReconnectHints`; and whitelisted inert `inactiveScheduleIntents`, `inactiveArchiveCoverage` and `inactiveCodexReconnectHints` when present. Unknown raw settings/preference members are not exported.
- `contextScopes`: schema-1 explicit-note file lists keyed by the SHA256 of the literal managed-root string. The key is a binding hint, not a durable vault identity.
- `scheduleIntent`: schema, historical schedule ID, original anchor, vault/parent, desired mode and `reconnectRequired: true`, or null. No handled-slot, effective-task, worker or success state is imported as execution authority.
- `vaultBindings`: managed-root and former vault/parent hints, explicit matching requirement and exact conversation brief pins. Path equality or matching bytes do not establish vault identity. There is no newly invented on-vault UUID.

Canonical serialization sorts object keys by JavaScript UTF-16 ordering, preserves array order and uses JSON primitive spelling with no extra separators. The SHA256 is over canonical `payload`; with optional coverage it is over canonical `{payload, coverage}`. This detects corruption and binds omission metadata. It is not a signature or proof of authenticity. Package text retains its own historical digest and Unicode count. There is no automatic migration for unsupported archive versions.

Selected input files must be ordinary single-link files no larger than 128 MiB. JSON duplicate members, nonfinite numeric values and nesting beyond 48 levels are rejected. Export checks both the canonical payload and the exact final pretty-printed UTF-8 envelope including its trailing newline against 128 MiB. The final check happens before any publication stage or destination is created. The observed near-limit public regression first reproduced an oversized unrestorable output, then passed with refusal, exact retained file byte count/SHA256 unchanged, no truncated reply and no provider replay. The source fixture is a compact valid retained record; its temporarily disconnected settings are separately preserved so history polling does not repeatedly render a giant reply.

The archive never reads or copies Codex managed homes, auth/account/session/token/cookie stores, readiness/private certificates, diagnostics, caches, locks or the whole application-data tree. User-entered conversation/excerpt text is preserved, so this is a credential-store exclusion policy, not a promise to scrub secrets a user pasted into a conversation. Only Companion's own canonical `codex/setup.json` is read as an explicit preference source. Ordinary parent/leaf identity checks guard it; export projects exactly `executable`, `project`, `vault`, `sandbox` and `reapprovalRequired: true`. Absolute control-free paths and the known `mxc`/`elevated` enum are validated. Irrelevant/private/readiness members in that file are excluded. These are inert reconnect hints, not restored sandbox permission or connection state. Import stores and displays hints separately, keeps current own setup bytes/UI fields unchanged and requires the existing explicit Check Codex setup workflow to reapprove. Current own preferences and inherited archived hints survive reexport separately. The observed fixture checks differing source/current preferences, private canaries, restart persistence and no RPC/model/task actions; it never opens managed-home/auth/certificate files or runs a probe.

## Incomplete archives and pending-only copies

Active requests and unsaved main-process overlays block every archive scope. They cannot be silently omitted. The observed recovery repairs storage and uses #10's existing explicit local Save, which compares the last published digest under the guarded history lock. The acceptance case confirms the latest retained text then enters a complete saved-history export without another provider submission. Memory-only overlays still cannot survive a process exit if local storage refuses the save.

Any `.pending` history file blocks complete export. Explicit review inventories only bounded ordinary single-link direct-child files with restricted basenames. Validated conversations show their complete retained JSON for inspection; unknown readable data receives an opaque recovery label. Aliases, unreadable files, unsafe names or excessive recovery size remain blocked. Inventory does not promote, delete, rename or repair those files.

After inventory, the user may explicitly choose a **saved-history-only** archive. The UI states it is incomplete, shows the preserved folder and warns that files may be the only copies of a reply and need separate copying before closing or moving the installation. The output omits pending bytes and carries integrity-bound `coverage: {mode: "saved-history-only", omitted: [...]}`. Each omission contains only a restricted basename, SHA256, byte length and `validated-conversation`/`unknown-data` kind. The exact pending inventory is revalidated before publication.

Restore retains that coverage only as inert metadata. It cannot manufacture the absent text or recreate/promote a pending file. Reexport carries prior coverage under `settings.inactiveArchiveCoverage`, even when the new installation has no current pending files. The observed workflow separately preserves the unresolved originals, restores only durable history, and verifies both original byte sequences remain unchanged. An incomplete archive is not a complete backup of those recovery bytes.

## Task reconnect and failure policy

Imported cadence is stored separately and remains inert during restore and startup. No live schedule file, task registration, old handled-slot or catch-up admission is copied. A separate select/preview/confirmation reconnects it. The preview discloses the original anchor, desired mode, current vault and that historical missed slots are skipped during reconnection; subsequent checks retain the anchor.

Reconnection uses a fresh local UUID and the current installation action, absolute schedule-file path and existing TaskScheduler ownership/policy checks. The original archived task ID is never used to change the old installation's task. An unrelated current schedule blocks reconnection; foreign actions and changed owned policies require separate repair. Under history and schedule locks, confirmation revalidates the selected intent/current schedule and durably reserves the local ID disabled/pending before registering. Only a successful OS operation is followed by a connected receipt and requested effective mode.

A failed registration retains the same disabled/pending reservation. A final-write failure can have an ambiguous task outcome; the UI says the task or final write may have succeeded and requires a fresh inspection. Retry reuses the reserved ID and inspects actual ownership before changing anything. A recorded connected state still requires effective-task inspection; repeat preview is mutation-free when the owned task and requested policy match. The controlled failure/restart/retry case verifies the same UUID, preserved original task, unchanged copied vault and no model submission. It does not establish native Task Scheduler registration behavior.

All application paths below are relative to the pinned canonical application-data root unless stated otherwise. Archive code never recursively copies these locations.

| Path or pattern | Content and lifecycle |
| --- | --- |
| `conversations/<conversation UUID>.json` | Full durable history, exact source-bearing packages, messages, pins and scope; current history authority. |
| `conversations/<UUID>.pending` | Existing Conversations staged full record. May contain the only retained reply. Never auto-promoted or deleted by archive inventory/export. |
| `conversations/archive-<UUID>.pending` | Archive addition stage containing a full imported record. Exclusive publication; own safe cleanup only. A parent-identity change leaves it preserved. |
| User-selected output parent `/.companion-archive-<UUID>.pending` | Synced full output archive before exclusive publication. May include source-bearing history. A replaced parent blocks publication and cleanup; the actual parent-replacement acceptance case verifies the retained original stage and untouched outside tree. |
| `settings.json` | Current vault/parent settings; archive reads an explicit projection and keeps current configuration on restore. |
| `codex/setup.json` | Companion-owned user preferences only: executable/project/vault/sandbox are projected as inert hints. The raw file and its unknown/private fields are never copied; current setup is never overwritten by import. No managed-home traversal occurs. |
| `archive-codex-hints-<archive UUID>.json` | Immutable inert `{schema, archiveId, preferences}` with exactly the four whitelisted preferences plus `reapprovalRequired: true`. No authentication, permission or ready authority. |
| `.archive-codex-hints-<UUID>.pending` | Flushed hint metadata stage with the same strict inert schema before exclusive publication; guarded own-stage cleanup only. |
| `context-settings-<managed-root SHA256>/notes.json` | Current explicit-note inclusion paths, no copied note bodies. Archive changes only individually reviewed inclusions. |
| Same context directory `/notes-<UUID>.tmp` | Flushed note-scope publication stage; paths only. Failure or directory replacement may retain it. |
| `archive-intent-<archive UUID>-<SHA256(sourceRoot + LF + targetRoot)>.json` | Immutable inert imported cadence record: schema, archive ID, source/target roots and whitelisted intent. Exportable as inactive settings. |
| `.archive-intent-<UUID>.pending` | Inert cadence metadata stage, not source text or execution permission. |
| `archive-coverage-<archive UUID>.json` | Immutable inert prior incomplete-archive coverage, restricted omitted basenames/digests/lengths/kinds. Never pending payload bytes. |
| `.archive-coverage-<UUID>.pending` | Coverage metadata stage with the same restricted inert fields. |
| `schedule.json` | Existing live schedule authority, changed by archives only after a separate explicit reconnect. Includes pending/connected `archiveReconnect` provenance, fresh local ID/current action, current handled-slot and operational task state. It is never copied wholesale into an archive. |
| `.archive-reconnect-<UUID>.pending` | Flushed local reconnect schedule stage, including paths/receipt/task state; no conversation text or credentials. |
| Memory-only approval/review maps and unsaved overlays | Full reviewed/unsaved text can exist in main memory. No reusable approval tokens or overlay CAS authority enter an archive. |

Vault `.intake` ledger, suppression/annotations, approved brief files, capture/revision material and #11 `.ideas` journals/only-copy writing remain separate vault authority. Archive matching reads exact selected retained briefs; reviewed note inclusion reads only individually mapped notes. It does not copy these vault trees, scan/reconnect producer folders, restore ledger snapshots or erase retained writing. Existing independent exports and provider submissions have separate lifecycles. This inventory supports later #12/#13 cleanup design but does not implement their deletion/revocation contracts.
