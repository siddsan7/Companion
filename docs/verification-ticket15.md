## Matched protocol and dispatch

`app/comparison-fixtures.js` owns version-1 plausible card-recall, weak sheet-nesting and misleading continuous-press passages, explicit limitations, and two versioned prompts. The labels and passages are inspectable as synthetic material. They are not actual reel content, measured learning outcomes or reference answers. The fit label is omitted from model packages.

One approved MyTune brief version, digest and complete retained source snapshots are pinned for the run. Every method pair receives identical source/brief bytes, identified by `sharedInputDigest`; each full method package has its own digest. Main regenerates the exact serializer from the known fixture/prompt and pinned brief before dispatch. A changed or unavailable brief or selected input blocks sending. This workflow adds no imported capture or historical conversation source. It does not bypass the eligibility rules for ordinary conversations.

Both prompts request a useful grounded idea or justified `No Supported Connection`, source/project citations, limitations, and a feasible small test when appropriate. Both request a final answer up to 600 words. Only analogy adds explicit source-mechanism mapping to project conditions and its possible failure. These are instructions, not a semantic guarantee that an answer is correct. Human grounding/error feedback remains necessary.

Six stable slots represent three cases times two methods. Each slot permits one reviewed send and one bounded provider turn. A failed, interrupted or ambiguous attempt remains consumed. There is no automatic reroll, repair turn or replay after restart. A separate new comparison is visible new evidence. Each attempt uses a fresh ephemeral restricted provider thread without prior comparison dialogue.

The dedicated comparison serializer avoids the ordinary conversation contract's unconditional mechanism request. `ConversationProvider` and shared `runTurn` retain their existing lease, generation, sink-drain, isolation and capacity checks. Narrow renderer operations never accept arbitrary provider text or RPC/configuration. Ordinary callers omit the comparison option and retain their prior wire/history fields.

Main-only `comparisonPin` contains exactly `model`, `modelProvider`, `reasoningEffort` and `serviceTier`. The installed 0.163.0 schema export cited in [ticket 10](verification-ticket10.md) establishes these thread-start/response fields and the typed `Config.model_reasoning_effort` key. Comparison thread creation sends the requested model/provider/tier and that one config key. Returned effective values must match before `turn/start`; missing metadata is retained as null and blocks dispatch. No unsupported temperature, output-token cap or extra RPC was invented. The 600-word limit is a request, not a proven generation-token ceiling.

The run pins safe independent settings/capacity/harness provenance and a random process-local binding at initial review. Both main and provider recheck it before actual dispatch. A changed pin after any attempt makes the run incomparable and closes further dispatch. A restarted process cannot reuse the persisted binding as portable proof; it retains prior outcomes and requires a separate comparison for new attempts. A wholly pending run can review current evidence before its first attempt.

Production capacity and comparison-settings resolvers default to null. They have no fixture fallback. The existing production provider also requires actual managed authentication, verified isolation/inventory, an unexpired certificate and matching protected roots/account/configuration. Controlled evidence is explicitly labeled `controlled-fixture-not-live`; it never enables production readiness. Missing proof leaves local capture usable.

The entire LF-normalized package is counted in Unicode code points, capped at 32000 and any independently verified smaller bound. Nothing is silently shortened. Harness overhead and output headroom require separate evidence. Token-usage windows do not prove capacity, and a context count is not a monetary or output-token budget.

## Retained output, effort and feedback

The store retains each exact prompt/package, full aggregate actual reply, ordered per-item text/phase/completion, thread/turn/model metadata when observed, terminal/error state, requested/effective settings, usage availability and lifecycle timestamps. A single completed `final_answer` item on a completed turn is the final candidate. Otherwise the complete actual aggregate output is retained with an unavailable/ambiguous warning. Unknown phases, commentary, failed replies and long outputs are not silently removed or repaired. Candidate word count and a greater-than-600 deviation are retained without truncation.

`elapsedMs` is monotonic local elapsed time from before preflight to provider terminal handling, including intermediate persistence. It excludes initial intent and final publication and is not pure model generation time. An abandoned in-progress request has unknown/null elapsed after process restart, never a fabricated zero.

Usage is nullable and comes only from valid matching `thread/tokenUsage/updated` events observed by the active shared listener. The stored total/last counters and availability qualification follow ticket 10. They may be incomplete and are not billing, account usage or capacity evidence. There is no equal-consumption, statistical-reliability, composite-score or numerical-release-threshold claim.

All six terminal outcomes, including generation failures, enter scoring. Main persists a separate cryptographically shuffled `blindOrder` with unique `Sample <8hex>` aliases after generation. Its alias-to-slot/method mapping stays in main-owned storage. The scoring projection omits private slot IDs, generation labels, methods, prompts, settings, proof and effort metadata. The UI hides generation/source/package panes while scoring. Wording can still suggest a method; this is not a double-blind study or secrecy guarantee.

The accepted rubric preserves four independent integer ratings from 1 to 5: usefulness, surprise, grounding and ease of testing. Anchors at 1, 3 and 5, intermediate 2/4 guidance and unrelated example applications are inspectable in `app/comparison-rubric.js`. Every rating needs a short reason and material-error choice. A supported abstention can score well for grounding; generation failure is explicitly different. High surprise never removes a material-error flag.

Feedback binds the opaque alias, retained candidate digest and rubric version. Locked fresh reads preserve other feedback. Repeating the same confirmation is idempotent; a stale conflicting revision is rejected. UI drafts remain separate from saved feedback, and async returns are fenced by the current view epoch. The tests exercise real second-instance feedback conflict; no separate exhaustive late-view-return race matrix is claimed.

Only an explicit `Reveal methods and effort` action can retrieve the mapping/full audit, after all six outcomes have complete feedback still bound to their candidates. First `revealedAt` persists. Later scoring states that methods were already revealed. Revealing/scoring retained results needs no live authentication or current process proof.

The current comparison source package has synthetic fixture material and approved brief snapshots, not a capture/revision dependency graph. A brief may contain selected project/source quotations. Absolute paths retained in provenance are descriptors, not permission to remove original documents or unrelated files. Preserve independent rating reasons and useful output according to the user's selected deletion scope; do not equate a proposed experiment with an executed result. Vault `.intake/ledger.json` remains separate authority and must not roll back with application-history handling. Existing archive scopes do not implicitly include comparison records.

Storage pins the canonical application-data root and validates the ordinary direct-child directory identity around I/O. Linked directories, linked/nonordinary leaves and unexpected hardlinks are rejected. Cross-process kernel ownership protects mutations. Creation is exclusive; updates use flushed stages and atomic replacement. Windows transient rename retries reuse only the same stage for about one second and never retry generation. These tests do not establish arbitrary filesystem race immunity.

A fresh intentional read under the mutation lock establishes that mutation's expected durable bytes. Only successful own publication advances its active baseline. Read-only list/poll calls cannot bless another writer's edit for an already running request. Final storage failure retains a cloned interrupted overlay and warning. Lists union durable filenames with overlay IDs, so a missing file does not hide the refused output.

Explicit local Save reads the ordinary existing file through the same guard and compares its exact bytes with the last successful owned serialization digest. It never establishes a new baseline from a conflict, recreates a missing identity, overwrites another writer or starts a model turn. Restoring the exact last durable bytes then saving can recover the overlay. If storage cannot be repaired, the user must copy the visible retained output before closing; process exit cannot preserve bytes storage refused. No separate comparison archive/export feature is claimed.
