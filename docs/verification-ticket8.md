### Capacity decision

D36-I04 requires separate room for instructions, reasoning and output. The 475,000-token context window in the App Server report equals the bundled catalog’s 500,000 multiplied by 95%. The independent published model specification lists 1,050,000 context tokens, 922,000 input tokens and 128,000 output tokens for the API. Those limits do not establish the effective limits of this managed ChatGPT route. [OpenAI model specification](https://developers.openai.com/api/docs/models/gpt-6.2-sol)

The proposed 12,000-code-point bound allows at most 48,000 bytes of UTF-8 text before JSON escaping. The three compact serialized request bodies contained 3,981 bytes each after replacing the user text with an empty string. Quotes, control characters and unpaired surrogates can increase wire length. Provider tokenization also accounts for message framing. Neither UTF-8 byte length nor wire length proves the input token count for this model. OpenAI’s public tokenizer mapping at the inspected revision has no GPT-6.2 Sol entry. The App Server schema inspected here has no pre-dispatch token-count method. The independent Responses API token-count endpoint would require a separately supported integration. [Tokenizer model mapping](https://github.com/openai/tiktoken/blob/79dc2c0533685b893616c78160b5d9e40876e724/tiktoken/model.py) · [Responses token counting](https://developers.openai.com/api/docs/guides/token-counting)

The installed experimental schemas for `turn/start`, `thread/sample` and `thread/settings/update` expose effort or output shape but no per-request token count or output-token cap. Account and thread usage report completed work. The release source estimates history size at about four bytes per token. That estimate would put the 61,323 user-text bytes in the reserve sample at about 15,331 tokens, while the hosted provider reported 58,861 input tokens including framing. Automatic compaction could change approved content and conflicts with D36-I03. [Ordinary provider request fields](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/codex-api/src/common.rs) · [Codex history estimates](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/core/src/context_manager/history.rs)

The 723 reported output tokens include any model framing and reasoning. The request fixed low reasoning effort and low verbosity and supplied no enforced output reserve. The 12,000-code-point proposal therefore remains unverified. To open chat, establish a route-specific supported bound on the complete framed input and a separate reasoning/output allowance, then bind both to the same live certificate and check them before dispatch. A change in account, model, settings, tool schema, catalog, configuration, roots or executable invalidates the evidence. Comparison qualification additionally requires independent confirmation of provider, reasoning effort and service tier. The ordinary thread reported null effort and tier. Scheduled reminders still require a real scheduled-worker isolation and lifecycle check.

### Repeating the checks

On Windows, `node scripts/check-signed-chat-request.cjs <disposable-staging-root> --send-one-synthetic-turn` uses the existing interactive sign-in and sends one fixed setup prompt. Use the Companion qualification directory under Temp with its own profile, project and vault. The script verifies available primary subscription capacity, rechecks the account and effective configuration against the same in-memory isolation certificate, and verifies the actual model, thread, turn, full input, tool digest and metadata. It prints a redacted result. After the writer exits, cleanup verifies the original directory and the referenced files by Windows volume, file identity, creation time and content digest. It retires verified files by handle and removes only empty verified directories. A crash, changed or unexpected entry, active handle, or interrupted cleanup can leave some or all of the raw trace on disk. When cleanup cannot finish, the command exits unsuccessfully and reports the staging directory name for manual inspection. The result grants no production readiness. The release tracer stores local request bodies and responses during the check. [Pinned upstream trace implementation](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/rollout-trace/src/inference.rs)

For fault handling, `node scripts/check-chat-request.cjs <absolute-codex-executable>` uses an unsigned local stand-in without hosted inference. D07-I04 and D35-I05 require actionable failures and preserved local work. The integration verification instructions call for simulated auth failure, offline operation, limits, partial replies, cancellation and restart. A genuine quota or service failure can be recorded if it occurs naturally. The spec does not require inducing one. [Companion spec](local-second-brain-spec.md)

## Runtime and checks

`app/codex-rpc.js` owns one private child process and JSON-lines connection. It rejects server-initiated capability requests. `app/codex-policy.js` builds the dedicated managed-home profile: explicit MXC/elevated selection, root deny, minimal platform reads, isolated working directory read, protected vault/project deny, command network disabled, no approvals, controlled instructions and disabled tool/skill/memory/hook/connector surfaces. It never modifies the user's Codex home.

`app/codex-isolation.js` audits effective layers before probing. `command/exec` selects the named profile explicitly. The bundled native Win32 helper avoids managed-runtime/crypto initialization; `app/codex-probe.js` verifies binary, LF-normalized C/build-source and manifest hashes before copying it exclusively into the isolated directory. A host-verified positive marker must be readable directly and through `CreateProcessW` child launch. Random markers in actual vault/project folders must return Win32 `ERROR_ACCESS_DENIED` via direct, child-process, case-variant, extended-prefix and junction paths. Missing files, child-spawn failure, model refusal and absent marker text do not count as denial. Owned canaries and junctions are removed individually.

Root builds the reviewed artifact with `scripts/build-codex-probe.ps1` (MSVC 14.44.35207, Windows SDK 10.0.26100.0, `/Brepro`, no CRT, Kernel32 only). `app/native/codex-read-probe.json` pins the compiled binary and normalized source/build hashes. The reviewed first binary hash is `8af4dc725326a0d654df0c3a66f07525ba87ab5fd09200a504bd59262c407576`. Rebuild/review is required when pinned source or build inputs change.

Probe selection was evidence-driven: PowerShell initialization failed with `8009001d`; standalone Node failed with a CSPRNG assertion even under a separate disposable implicit-profile diagnostic. Neither startup failure counted as denial. The reviewed native helper reads through Win32 APIs without CRT/Crypto initialization and distinguishes child-spawn failure from file access denial.

`app/codex-turn.js` creates a new ephemeral thread for each turn and checks returned roots, profile and instruction sources. Only terminal `completed` succeeds. Interruption waits for terminal confirmation and closes the child after a bounded timeout. No `thread/shellCommand`, resume, fork or external token login is exposed.

The isolation certificate is process-local, visibly expires after ten minutes, and is invalidated by changed executable/config/root/account evidence. A fixture can enable the synthetic test control but can never set live `ready`. A completed live synthetic turn also leaves `ready:false` until independent prompt/tool inventory evidence is established. Persistent readiness data is evidence, never an imported certificate.

Root ran `npm.cmd test -- tests/codex.spec.js` after the final production edit: seven passed. Syntax checks passed for the new modules/scripts and bootstrap files. The synchronized combined suite passed 42 tests with one file-symlink capability skip. Exact-commit independent approval remains required before integration. The user deferred signed-in live checks to #16; fixture success does not change their pending status or enable chat readiness.
